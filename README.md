# Розробка системи автономної візуальної навігації для БПЛА

Магістерська робота. Автономний проліт квадрокоптера DJI Robomaster TT
(Tello) крізь обруч за даними монокулярної камери.

## Мета

Підвищення ефективності та стабільності автономної навігації БПЛА в
GPS-дефіцитних середовищах шляхом порівняльного дослідження методів
візуальної детекції та стратегій керування.

## Архітектура

Дрон з'єднаний з ноутбуком по Wi-Fi: ноутбук приймає відеопотік,
обробляє кадри й надсилає команди керування. Уся обробка — на ноутбуку.

```
                  ┌────────────────────────────────────────────┐
   відеопотік     │  детекція  →  оцінка  →  контролер         │
  ───────────────►│  обруча       пози       IBVS/PBVS/гібрид  │
     (кадри)      │                                            │
                  └──────────────────┬─────────────────────────┘
   команди керування                 │
  ◄─────────────────────────────────-┘
```

| Модуль | Призначення |
|---|---|
| `src/detection/` | детектори обруча за спільним інтерфейсом + вибір треку |
| `src/pose/` | оцінка 3D-пози обруча (розклад коніки) |
| `src/control/` | стратегії керування (IBVS, PBVS, гібрид) + ПІД |
| `src/sim/` | модель дрона, камери та деградацій для симуляції |
| `src/synth/` | генератор синтетичних навчальних даних |
| `src/viz/` | візуалізація детекції та команд |
| `experiments/` | навчання, бенчмарки, порівняння |

## Розпізнавання обруча

Основний результат роботи. Порівнювалися дві архітектури (YOLOv8n і
YOLOv11n) на кількох варіантах навчального набору.

**Оцінка на реальних кадрах:** 140 кадрів, знятих на iPhone 14 у
чотирьох сценах (Kitchen, Balkony, Outside, Room) і розмічених вручну.
Жодна з цих сцен не входила до навчання. Поріг упевненості 0.25,
збіг за IoU ≥ 0.5.

| Модель | Precision | Recall | F0.5 |
|---|---|---|---|
| **yolov8n_mixed2** | **0.976** | 0.879 | **0.955** |
| yolo11n_mixed | 0.937 | 0.843 | 0.916 |
| yolo11n_mixed2 | 0.907 | 0.907 | 0.907 |
| yolov8n_mixed | 0.932 | 0.779 | 0.896 |
| yolov8n_full (без синтетики) | 0.378 | 0.771 | 0.421 |

Метрика — **F0.5**, а не F1: помилкова детекція веде дрон у
неправильному напрямку, тоді як пропуск кадру лише подовжує пошук.
Тому точність важить удвічі більше за повноту.

**Висновки:**

- Додавання синтетичних даних піднімає precision з 0.378 до 0.976
  при майже незмінній повноті. Виграш іде саме через хибні
  спрацювання, а не через кількість знайдених обручів.
- Вибір навчального набору впливає приблизно вчетверо сильніше за
  вибір архітектури: розкид F0.5 між наборами 0.53, між архітектурами
  максимум 0.12.
- Оптимум складності набору — посередині ланцюга (`mixed2`), а не в
  максимумі. Подальше ускладнення синтетики метрики погіршувало.
- Між YOLOv8n і YOLOv11n стійкої переваги немає: на п'яти парах
  наборів рахунок 3:2 на користь v8n.

На тестовій вибірці Roboflow обидві архітектури дають F1 ≈ 0.99 при
84–87 FPS на GTX 1650; класичний детектор кіл на OpenCV — F1 ≈ 0.02.
Ці числа оптимістичні, бо тестова вибірка походить із тієї ж зйомки,
що й навчальна; саме тому основною оцінкою є реальні кадри вище.

## Калібрування камери

Внутрішні параметри камери потрібні для метричної оцінки пози. Для
зйомок використано iPhone 14; калібрування виконано за шахівницею,
що виводиться на екран монітора (друк був недоступний), 25 ракурсів.

| Параметр | Значення |
|---|---|
| роздільність | 1920×1080 |
| фокусні відстані | fx 1811.8, fy 1816.8 px |
| поле зору | 55.8° × 33.1° |
| RMS репроєкції | 1.56 px |

Результат — `calibration/iphone14_1920x1080.json`. Шаблон
генерується скриптом і виводиться на екран у відомому масштабі.

## Оцінка пози обруча

Проєкція кола є еліпсом, тому класичний `solvePnP` за кутами
непридатний. Використано **розклад коніки**: матриця коніки в
нормалізованих координатах приводиться до власного базису, звідки
відновлюються центр і нормаль площини обруча.

Метод дає **два математично валідних розв'язки** (дзеркальна пара),
які проєктуються в той самий еліпс. Двозначність знімається часовою
консистентністю — вибором гілки, ближчої до нормалі з попереднього
кадру.

На синтетиці з відомою істиною похибка позиції не перевищує 1.6 см,
похибка нормалі — менша за 0.1° (`experiments/results/pose_validation.txt`).

Модуль `src/pose/pnp_solver.py` містить обидва методи: розклад коніки
для круглої цілі (використовується в системі) і класичний `solvePnP`
за 4 кутами для прямокутної — як опорний для порівняння.

## Стратегії керування

Реалізовано три стратегії за спільним інтерфейсом:

- **IBVS** (image-based) замикає контур на піксельних помилках —
  зсуві центру еліпса та його круглості. Пози не відновлює, тому
  нечутливий до похибки калібрування.
- **PBVS** (position-based) відновлює метричну позу й веде дрон у
  точку підльоту на осі обруча, а вже звідти — на проліт.
- **Гібрид** перемикається між ними: PBVS для виходу на вісь, IBVS
  для фінального наведення.

Перевірка на замкненому стенді в симуляції (30 запусків з різних
початкових положень і нахилів обруча) дає частку успішних прольотів
93% для гібрида проти 63% в IBVS і 47% в PBVS.

**Відоме обмеження:** при старті збоку траєкторія може проходити
через ракурс, у якому обруч видно з ребра, і детекція розривається.
Фронтальні старти відпрацьовують без втрат кадру.

## Дані

**Реальні.** [Roboflow `aims-akfyb/drone-racing-okmii`](https://universe.roboflow.com/aims-akfyb/drone-racing-okmii)
v1, CC BY 4.0. 507 зображень. Класи `ringb`/`ringg`/`ringr` злито в
єдиний `ring` — колір для задачі не має значення. Набір знято за
кілька сесій в одному приміщенні й розмножено аугментацією, тому
самого його недостатньо.

**Синтетичні.** Генератор `src/synth/` рендерить обручі з
випадковими ракурсами, нахилами, освітленням і тлом. Обов'язково
включає негативні приклади та кола-дистрактори — без них модель
вчиться реагувати на будь-який овал.

**Оціночні.** 140 кадрів із власних зйомок, розмічених вручну
(labelme). Використовуються тільки для оцінки, у навчанні не брали
участі.

Датасети й ваги моделей у репозиторій не входять (див. `.gitignore`).

## Встановлення

```bash
python3 -m venv .venv
.venv/bin/pip install -r requirements.txt
```

**Важливо про CUDA.** Свіжий `torch` з PyPI зібраний під CUDA 13.0.
На драйверах, що підтримують лише CUDA ≤ 12.2 (напр. 535), він мовчки
працює на CPU без повідомлення про помилку. Потрібна збірка cu121:

```bash
.venv/bin/pip install -r requirements-cuda.txt \
    --index-url https://download.pytorch.org/whl/cu121
.venv/bin/python -c "import torch; print(torch.cuda.is_available())"  # має бути True
```

## Експерименти

```bash
# Калібрування камери за шахівницею з екрана
.venv/bin/python -m experiments.show_calib_pattern
.venv/bin/python -m experiments.calibrate_camera --video calib.mp4 --name iphone14

# Генерація синтетичного набору
.venv/bin/python -m experiments.generate_synthetic_dataset --out datasets/synthetic_hoops

# Навчання детекторів
.venv/bin/python -m experiments.train_detectors --data datasets/hoops_mixed_v2/data.yaml

# Точність і FPS на тестовій вибірці
.venv/bin/python -m experiments.benchmark_detectors --data datasets/hoops/data.yaml

# Оцінка на розмічених реальних кадрах (основна метрика)
.venv/bin/python -m experiments.eval_labeled

# Збереження кадрів детекції для візуальної перевірки
.venv/bin/python -m experiments.save_detections --video datasets/real/kitchen.mp4 \
    --weights models/yolov8n_mixed2.pt --track

# Порівняння контролерів на замкненому стенді
.venv/bin/python -m experiments.closed_loop_sim

# Інтерактивне вікно: сцена, камера дрона, підказки алгоритмів
.venv/bin/python -m experiments.live_sim
```

`live_sim` відкриває вікно з трьох панелей — вигляд сцени зверху,
зображення з камери дрона й вихід алгоритмів. Керування: `SPACE`
пауза, `R` перезапуск, `1`/`2`/`3` вибір контролера, `S` знімок,
`Q` вихід.

Порівняння контролерів працює **без дрона**: команди не надсилаються,
а записуються в CSV і візуалізуються.
